## MAJOR-1 — Pinned rewind/shrink markers do not compose (content leaks back)

**Severity:** Major — defeats the core rewind guarantee (spec §2.5 success criterion #1: *"shed it so
that no subsequent inference sees it"*).

**Symptoms (two manifestations of one root cause):**

### (a) Two pinned rewinds with distinct spans → only the oldest is applied
When an agent rewinds mistake A, continues, then rewinds mistake B, only mistake A is hidden.
Mistake B's content **leaks back** into the model's view on every subsequent inference.

```
probe: two pinned rewinds (hideEntryIds ["e1","e2"] + ["e3","e4"]) on distinct toolGroups
  result: grep hidden:true | read hidden:FALSE | len:9 (expect 7)
```

A third rewind is likewise dropped — N pinned rewinds collapse to only the first (oldest-seq).

### (b) Pinned shrink after a rewind → shrink silently no-ops
When an agent rewinds a span, then shrinks a result that lived *after* that span, the shrink does
not apply. The model sees the **original (un-shrunk) content**, not the agent-authored replacement.

```
probe: rewind hides grep (e1,e2); pinned shrink (pinnedEntryId "e4") targets the read
  result: read content:"READ_OUT" (expect "[SHRUNK]")
```

**Root cause:** `filterPipeline` (`src/transforms.ts:1318`) applies rewinds **sequentially** in a
loop — each rewind calls `applyRewind(m, remove)` which shrinks the working array `m`. But the
pinned resolvers `resolvePinnedHide` (`src/transforms.ts`) and `resolvePinnedShrink` walk the
**full `branchEntries`** against the **reducing `m`**. The entry→message alignment is only valid
for the *original* message list; once a prior rewind removes messages, the walk:

1. maps entry ids to **wrong** (post-removal, shifted) message indices, and
2. trips the alignment guard `if (msgCursor + y > messages.length) return []` (or `return null`)
   the moment the walk reaches entries beyond the now-shorter `m` — **discarding every removal
   index collected so far** (a fresh `[]` is returned, not the partially-built `remove` array).

So every pinned marker after the first resolving rewind in a pass resolves to `[]`/`null` → no-op.

**Why the 954-test suite missed it:**
- The composition test (`test/transforms.test.ts` "spec/10 §1.9 bullet 1") uses **unpinned**
  (legacy) rewinds and *expects* the second to no-op — it treats spec/06 §11's "two distinct
  removals" narrative as an erratum. That is correct for the legacy path (where `turnHasAdvanced`
  gates the second rewind to no-op anyway), but the **pinned** path — the *production* path, since
  `captureHideEntryIds` always populates `hideEntryIds` — was never tested for multi-distinct-span
  composition.
- All pinned-hide unit tests exercise **single** rewinds; none compose two with disjoint
  `hideEntryIds`. Same for pinned shrinks after a rewind.

**Production impact:** the production `mulligan_rewind` tool always sets `hideEntryIds`
(`src/tools/rewind.ts` `resolvePreview` → `captureHideEntryIds`), and `mulligan_shrink` always sets
`pinnedEntryId` when the target matches at creation (`src/tools/shrink.ts` `resolveTargetEntryId`).
So this is not a theoretical/legacy-only path — it is the normal agent workflow whenever an agent
rewinds more than once, or rewinds then shrinks.

**Evidence commands** (reproduce deterministically, no model/Pi needed):
```bash
node --input-type=module -e 'import { filterPipeline } from "./src/transforms.ts";
  /* two pinned rewinds, distinct hideEntryIds — see validate.sh Phase 8 */'
```

**Suggested fix direction (for the fixer, not applied here):** pinned markers resolve by *stable
entry identity*, not by relative position — so they should be resolved against the **original**
`event.messages` (pre-any-removal) and their removal sets **unioned**, then applied once. The
sequential "resolve against the already-reduced array" semantics (spec/03 §5) only matter for the
*legacy relative* resolvers; the pinned path is identity-based and independent of other markers.
At minimum, the alignment guard in `resolvePinnedHide`/`resolvePinnedShrink` should not discard
already-collected indices when the branch is longer than the reduced `m`.

## MINOR-1 — `mulligan_checkpoint` refuses if called before any real conversation message

**Severity:** Minor (UX / edge case).

When `mulligan_checkpoint` is the agent's *very first* action (before any user→assistant exchange),
`setCheckpoint` (`src/markers.ts`) walks `getBranch()` backwards for a `message` entry with a real
`role` and finds none (only the session header exists) → returns `{error: "no stable entry to
checkpoint"}` → the tool refuses.

```
E2E probe at session_start:
  Mulligan: refused — could not set checkpoint: no stable entry to checkpoint
```

This is *defensible* (the tool description says "Use before a speculative sub-task," implying prior
context), and the BUG-003 fix deliberately avoids labeling the raw leaf. But the refusal is
surprising for an agent that checkpoints aggressively, and the error text does not tell the agent
*why* (no prior conversation) or *what to do* (emit a message first). A clearer message or a
fall-back to labeling the session-start position would improve UX. Low impact.

## MINOR-2 — `VERIFICATION.md` is stale re: settings-driven disable (documentation drift)

**Severity:** Minor (documentation inconsistency, not a code bug).

`VERIFICATION.md` DoD #4 note states:

> `src/index.ts:29` calls `setConfig(undefined)` → `DEFAULT_CONFIG` (`enabled:true`) at load. The
> factory does **not** read real `settings.mulligan` (`index.ts:28`: "reading real settings.mulligan
> is v1.1").

The **actual** `src/index.ts` calls `setConfig(loadMulliganConfig(process.cwd()))` — it *does* read
real merged Pi settings (global `~/.pi/agent/settings.json` + project-local `.pi/settings.json`).
Settings-driven disable works end-to-end (verified by `validate.sh` Phase 6: `enabled:false` in
project settings → extension loads + no-ops). The VERIFICATION.md note is a stale snapshot from
before `settings.ts` shipped; it should be corrected so future maintainers do not believe disable is
unimplemented. The same note also claims "audit + checkpoint are intentionally non-gated," which
contradicts the BUG-005 fix (audit *is* now gated on `config.enabled`). The **code** is correct in
both cases; only the prose report is wrong.
